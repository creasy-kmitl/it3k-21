## Architecture / contracts

`department.code` is a nullable unique stable string; migration backfills the two existing seeded names only, admin can set/unset via a privileged endpoint if names differ. New `leadership` records (`id` runtime UUID, `departmentId`, `role:'head'|'vicehead'`, `userId?`, `name`, `nickname?`, `phone?`) and `leadership_social` (`id` UUID, `leadershipId`, `platform`, `value`) live in D1. Nullable/empty phone both accepted; persist empty as `null` for consistency. Child socials are replace-on-update in one D1 transaction/batch; deleting a leader cascades socials; deleting a user detaches the record (`ON DELETE SET NULL`); deleting a department with records must be rejected by FK/restrict.

Backend: chain handlers on `new Hono()` in `apps/server/src/routes/leadership.ts`, export `typeof routes`, mount at `/api/leadership` from `apps/server/src/index.ts`; use `@hono/zod-validator` and Zod 4 (`z.email()` if an email is ever needed, not deprecated `z.string().email()`), typed `c.json(..., status)`. `apps/web/src/lib/leadership.ts` imports that type **only** and calls `hc` with `credentials:'include'`; no untyped `fetch`/`any`. Separate public-summary SELECT from contact SELECT: GET/list/detail/attach-user-search never return phone/social, including nested objects, error bodies or logs. `POST /:id/reveal` returns contact only after a server-side audit event; send `Cache-Control: private, no-store` and never persist revealed payload in TanStack Query cache/localStorage.

**Exact API contract** (all under `/api/leadership`, authenticated/non-banned; response errors `{message:string}` plus `issues` for 400):

| Method/path | Input | Success | Authorization |
|---|---|---|---|
| `GET /?q=&departmentId=&page=1` | `q` trimmed ≤64 code points, bounded nonempty department ID (seed IDs are hex, not UUID), page integer ≥1 | `200 {items: Summary[],page,hasMore}` sorted department creation order, role head then vicehead, name | any logged-in user |
| `GET /:id` | UUID param | `200 Summary` | any logged-in user |
| `GET /users?q=&page=1` | trimmed q ≥1 and ≤64; page ≥1 | `200 {items:[{id,name}],hasMore}`; exclude already attached accounts, limit 20 | admin or Tech/Live/Registration head/vicehead |
| `POST /` | `{departmentId,role,name,nickname?,phone?,userId?,socials:[{platform,value}]}` | `201 Summary` | admin or Tech/Live/Registration head/vicehead |
| `PATCH /:id` | partial create fields except id; self-manager restricted to `{nickname,phone,socials}` | `200 Summary` | manager or attached non-manager head/vicehead self |
| `DELETE /:id` | UUID param | `204` | manager only |
| `POST /:id/reveal` | `{confirmed:true}` after user accepts dialog (reject other bodies) | `200 {phone:string|null,socials:[{platform,value}]}` | any logged-in user, only after audit succeeds |
| `PATCH /api/departments/:id/code` | `{code:'tech-live'|'registration'|null}` | `200 {id,code}` | admin only; uniqueness collision 409 |

`Summary` = `{id,departmentId,departmentName,role,userId,name,nickname,displayName,canEdit,canDelete}`; permission flags computed **server-side** and per-row. Unauthorized login 401, logged-in denied 403, not found 404, duplicate seat/attachment/code 409, invalid 400, audit unavailable 503, unexpected 500 (no raw exception or PII). Reject unknown JSON keys (Zod `.strict()`), overlong names/socials and unsafe links; do not accept caller-supplied ID or role/department in self-edit. Search is case-insensitive for ASCII only; never claim Thai typo-tolerance.

```ts
import { hasRole } from "@it3k/auth/permissions";

export type Actor = {
  id: string;
  role: string | null;
  departmentCode: string | null;
  banned: boolean;
};
export type Target = { userId: string | null };
export type Action = "create" | "update" | "delete" | "attach" | "reveal";

export function allowed(actor: Actor | null, action: Action, target?: Target): boolean {
  if (!actor || actor.banned) return false;
  if (action === "reveal") return true;
  if (hasRole(actor.role, "admin")) return true;
  const leader = hasRole(actor.role, "head") || hasRole(actor.role, "vicehead");
  if (!leader) return false;
  if (actor.departmentCode === "tech-live" || actor.departmentCode === "registration") return true;
  return action === "update" && target?.userId === actor.id;
}
```

The route loads fresh actor `role,departmentId,banned` and joins department code from DB on every request (not from client/URL); never let self-update reassign attachment/seat. ## Risks / tradeoffs / open questions

- **Contact privacy**: confirmation and Axiom logging were requested for staff; plan enforces them for *every* viewer. Axiom transport does not guarantee durable ingestion synchronously; decide before coding whether D1 audit outbox/row is required to guarantee the user requirement under ingestion outages. Fail closed if the local audit step errors.
- **Identifiers**: Better Auth user IDs are text; do not use `z.uuid()` for `userId` without verifying actual IDs. New leadership/social IDs are UUIDs; department IDs seeded by SQL are hex, not canonical UUID, so `departmentId` needs a bounded nonempty string validator, not `z.uuid()`.
- **Department mapping**: names can change, codes are stable. Backfill only known seeded names; renamed/custom records need admin code assignment. Existing `department` delete currently clears user memberships; with leaders it must fail safely rather than orphan records.
- **Attached names**: `nickname` belongs to leadership row; `user.name` remains authoritative, so stored fallback `leadership.name` may become stale after user rename. Public display comes from JOIN; no denormalization sync job.
- **Socials**: platform/value rather than one column per service is the smallest extensible schema. Confirm whether multiple handles on the *same* platform or more than one vicehead per department are needed before removing uniqueness limits.
- **Scope of 401**: authenticated UI requires session; backend still returns JSON 401. Existing `/login` stays public. Login navigation should preserve no PII in URL or state.
