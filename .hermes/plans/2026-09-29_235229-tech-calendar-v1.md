## Decisions required before implementation

These are product-policy decisions, not details an implementer should guess:

1. **Authorization matrix:** who may create/edit an item; who may mark it `Confirmed`, `Ready`, `Live`, `Released`, or `Cancelled`; who is an approver; and who is a public publisher. Proposed safe default: any member (`isMember`) can read; only `admin` and Tech/Live seat holders can mutate Tech Calendar records; only `admin` can approve or publish. **Sub-decision:** the existing `isManager()` already grants admins *and every member* of any coded department (`tech-live` **and** `registration`). State explicitly whether calendar mutation reuses `isManager`, or narrows to `departmentCode === "tech-live"` (optionally seat holders only). Identify departments by `department.code`, never by name — names are admin-editable.
2. **Public calendar contract:** target URL/API consumer, data format, cache/refresh target, and which fields are public. Until approved, `visibility = "public"` must be rejected by the API rather than silently exposing data.
3. **Notification contract:** destination(s), recipient identity source, retry/acknowledgement behaviour, rate limits, and approval for outbound messaging. Do not send messages merely because a calendar record changes.
4. **Source-of-truth and synchronization:** which system supplies official schedules/results for TFT, VALORANT, and RoV, who confirms them, and whether imports are manual or automated.
5. **Conflict rules:** whether conflicts block saving or only require a recorded mitigation; the canonical identities for venues, stream channels, scoreboard operators, and release environments.
6. **Release environment vocabulary:** exact permitted values (for example, `development`, `staging`, `production`) and the required rollout/rollback approvers.

Record the Head’s answers in issue #12 before implementing Tasks 5, 12, 22, 24, or 25. This prevents staff-only privileges, public exposure, and notifications from being invented in code.

## Architecture / proposed approach

Add a `calendar_item` aggregate in D1 with normalized join tables for filterable relationships (departments, participants, dependencies, checklist entries, action items) and an append-only `calendar_item_change` audit table. Keep category-specific optional fields on the item itself for v1; do not introduce a separate table per event type.

Expose a typed Hono route factory at `/api/calendar`, following the existing route/dependency/authorization pattern. Build a private `/staff/calendar` route that uses a typed Hono client and TanStack Query; calendar grid/list rendering is a UI adapter over the same query data, not a second data model.

Deliver in vertical slices: private item listing first, then creation/editing, then operations/readiness, coordination/release details, conflict/audit controls, and only finally a public adapter if the decisions above are approved. Every mutation must write an audit record in the same D1 batch before returning success. Any write that depends on state the route read earlier (version, status, checklist completion, seat) must recheck it inside that batch with an `abortUnless`-style guard; a `WHERE` clause that matches zero rows does **not** fail a batch.

Store every instant as UTC epoch ms. `Asia/Bangkok` is a fixed UTC+07:00 with no DST, so there is no per-item `timezone` column; instead add small pure helpers (`bangkokDay(instant)`, `bangkokDayBounds(date)`) for the server (range filters, run sheet) and the web app (grouping, `Today`, form inputs), covered by the same fixed-offset test cases. `apps/web` does not depend on `@it3k/db` (it imports server *types* only), so it cannot import the schema's runtime constants: web-side option lists are typed against API-inferred types so drift is a type error, as `apps/web/src/components/department-icon.tsx` does for department icons.

### Tables and invariants

| Table | Required columns / invariant |
|---|---|
| `calendar_item` | UUID `id`; title; `start_at`, `end_at` (UTC timestamp-ms; no `timezone` column — see Architecture); mode/category/status; nullable internal `owner_user_id` (`on delete set null`); source; `last_confirmed_at`; visibility; risk level; integer `version` default 1 (used by Task 11, created now so PR 1 ships one migration); category-specific optional fields; `notes`; `archived_at`; created/updated timestamps. `CHECK (end_at > start_at)` plus enum `CHECK`s; `public` is never returned by public code until publisher policy is implemented. Change reasons live on `calendar_item_change`, not the item. |
| `calendar_item_department` | `(calendar_item_id, department_id)` unique; used by department filters and affected-party display. |
| `calendar_item_participant` | UUID; calendar item; nullable user FK or `external_name`; exactly one identity is present; records invite/acceptance state only after that state vocabulary is approved. |
| `calendar_item_dependency` | `(calendar_item_id, depends_on_calendar_item_id)` unique; no self-dependency; both IDs must exist; never permit a dependent to reference an archived record without an explicit warning. |
| `calendar_item_checklist` | UUID; item; label; sort order; nullable owner; boolean `done`; completed timestamp. Required templates are created only for Match/Broadcast/Technical check. |
| `calendar_item_action` | UUID; source item; title; nullable owner; optional due date; `open`/`completed`; optional target item. This is an action record, not a duplicate issue tracker. |
| `calendar_item_decision` | UUID; source item; body; actor; created timestamp. |
| `calendar_item_change` | append-only UUID; item ID; actor; impersonator; action; serialized old/new **non-sensitive** values; reason; created timestamp. **No foreign keys**, index `(calendar_item_id, created_at)` — follow `leadershipContactReveal` in `packages/db/src/schema/leadership.ts` so audit rows outlive the item and accounts they mention. No contact details, credentials, meeting secrets, or private notes may be copied here. |

### API surface

All routes use `requireJsonPosts`, `requireUser(deps)` and `requireMember`. Return `{ message: string }` with 400/401/403/404/409 as the existing API does (400 via `validate()` in `apps/server/src/middleware/validation.ts`, which adds `issues`). The server computes permission flags; the UI never re-derives them.

| Method and path | Behaviour |
|---|---|
| `GET /api/calendar` | Returns `{ items, page, hasMore, canCreate }`, matching the leadership list (`apps/server/src/routes/leadership/index.ts`, `PAGE_SIZE + 1` probe); each item carries `canEdit`. Query: `from`, `to`, `mode`, `category`, `status`, `game`, `ownerId`, `departmentId`, `riskLevel`, `q`, `page`. `venue`, `streamPlatform`, `environment` filters wait for Decision 5's canonical identities (PR 3). Exclude archived by default. |
| `GET /api/calendar/:id` | Private detail with joins, checklist, actions, decisions, dependencies, and audit timeline. |
| `POST /api/calendar` | Create a draft item. Validate duration, enum values, references, source, and category-specific requirements. Apply required live-operation checklist template when appropriate. |
| `PATCH /api/calendar/:id` | Partial update, reschedule, cancellation, archive, confirmation, and status transitions. Require a change reason for changes to time, owner, venue, stream, visibility, status, or release window. |
| `PUT /api/calendar/:id/checklist/:checklistId` | Toggle a checklist entry; preserve operator and completion time. |
| `POST /api/calendar/:id/actions` / `PATCH /api/calendar/:id/actions/:actionId` | Add and complete action items. |
| `POST /api/calendar/:id/decisions` | Add a meeting/handoff decision. |
| `GET /api/calendar/run-sheet` | Current Bangkok-day summary: next live item, next meeting, next release, on-call, and open blockers. |
| `GET /api/calendar/conflicts` | Read-only conflict evaluation for a candidate item or an existing item. It must not save anything. |

## Risks, tradeoffs, and open questions

- **Scope risk:** issue #12 is an epic. A complete Month/Week/Day calendar, coordination system, release tracker, public feed, conflict engine, audit trail, and notification system should be delivered as the private vertical slices above, not one oversized PR.
- **Authorization risk:** current Better Auth roles are coarse. Calendar powers are derived server-side in `policies/calendar.ts` from role, seat and department code — never from new Better Auth grants — which still changes access policy; obtain the Head’s approved matrix (including the `isManager` sub-decision) and test the server boundary before adding UI controls.
- **Privacy risk:** meetings, stream operations, contacts, and incident notes can contain sensitive information. Private/public serializers must be distinct; never return raw DB rows, audit JSON, credentials, or contact fields.
- **Time-zone risk:** D1 timestamps are instants, but every staff-facing grouping, form label, conflict calculation, and run-sheet boundary must be `Asia/Bangkok` (`UTC+07:00`). Browser-local dates must not determine event-day boundaries.
- **Audit tradeoff:** an append-only D1 table gives a durable application record; the existing `evlog` Axiom drain is asynchronous and cannot be represented as guaranteed audit delivery.
- **Dependency risk:** a rich calendar view probably needs a new UI dependency. Do not add one until Task 2 selects a package compatible with the installed React/TanStack versions and its accessibility/timezone behaviour is validated.
- **Data-source risk:** Sports/Registration/Coordination/Venue/PR-Art remain authoritative for their own inputs. Calendar records must retain `source` and `lastConfirmedAt`; unconfirmed information stays `TBD` and private.
- **No migration/backfill assumption:** there is no existing event calendar schema to migrate. If one is introduced before implementation, inspect ID and timestamp formats first and add a separate, reversible import plan.
